## Actors, assets and observable state

Actors are a local CLI/MCP client, an authorized HTTP operator or trusted reverse proxy, an untrusted HTTP requester, the upstream browser-tool provider, and an operator examining diagnostics. Protected assets include proxy credentials, per-session browser control, persistent profile contents, generated configuration, child processes, CDP capabilities/leases and usable session capacity.

For acceptance, an HTTP owner is **provisional** while initialization is incomplete, **active** after successful protocol initialization, **closing** during disposal, and **closed** when owned resources are released. These are behavioral terms, not required internal classes or storage records. Server shutdown closes admission before waiting for owners. A managed browser generation has an established browser identity independent of how many page targets currently exist.

Observation surfaces include protocol responses/session IDs, existing readiness/session diagnostics, request cancellation received by a controlled upstream, actual owned process exit, filesystem existence within an isolated test directory, profile reuse, port/capability behavior, CLI streams and exit status. A lack of log output alone never proves cleanup or secret protection.

## Requirements

### AR-001: Preserve the thin bridge and unrelated behavior

**Behavior.** Preserve upstream browser tool names, schemas, parameters, successful results, pagination/list-change behavior and supported protocol versions. Keep the two existing local introspection tools; do not introduce a browser-tool fork or extra local tools. The intended exceptions are the approved HTTP admission restrictions, correct cancellation propagation, removal of protected proxy material from launch-failure diagnostics, the ordinary-mode profile-use timing/normal tool-error behavior in AR-019–020, and the exact existing-dependency/humanize compatibility correction in AR-021–023. Preserve stdio/HTTP session isolation, existing profile/extension/proxy behavior outside those explicit corrections, eager managed-CDP readiness and current defended CDP/Docker paths.

**Acceptance.** Compare upstream/bridge contracts and representative successful calls against the same dependency/input identities: observe unchanged contracts and non-secret results; exclude schema rewrites or diagnostic redaction that corrupts ordinary page/tool content. Concurrent isolated sessions remain independently usable when one request is rejected, cancelled or disposed; exclude another session's child, profile, capability or configuration being modified. Existing client-abort, transient CDP forwarding and Docker IPC backpressure/send-error regressions continue to pass; exclude treating those pre-existing fixes as missing work.

### AR-002: Preserve component-specific platform support

**Behavior.** Preserve npm support on Linux x64/arm64, macOS arm64/x64 and Windows x64 with Node `^22.13.0 || >=24.0.0`; Docker remains Linux amd64/arm64. Preserve strict ESM/TypeScript and the existing CLI-only public package boundary. Do not broaden support, change Node/upstream MCP/Playwright or unrelated dependency versions, or infer platform success from the development host. The sole selected dependency exception is the future exact CloakBrowser 0.6.4 target and its necessary resolution effects under AR-021–023; its own engine range does not broaden the bridge's declared Node support. Cleanup, permissions, path handling and signals must respect each supported platform rather than assume POSIX behavior everywhere.

**Acceptance.** For each affected platform-dependent boundary, observe equivalent owner cleanup, profile preservation and diagnostic outcomes using supported native mechanisms; exclude passing Linux-only evidence as Windows/macOS verification. Record the existing Node 22 and 24–26 CI matrix separately from the broader declared engine range. Unsupported runtime diagnostics follow AR-013; exclude silently claiming a new platform/browser combination is certified. An unavailable required environment is reported as unverified, not passed.

### AR-003: Rejected initialization must reclaim capacity (SEC-001)

**Behavior.** Validate protocol admission and retain ownership of every provisional resource until initialization either succeeds or is rolled back. Rejection, exception, client disconnect, startup failure or cancellation must not leave an uninitialized owner beyond terminal cleanup. Successful initialization creates one active session and its metadata exactly once; rejected initialization must not publish a usable session ID. Preserve configured capacity, body limits and idle-expiry semantics; expiry is not a substitute for failed-initialization cleanup.

**Acceptance.** With maximum sessions set to one, independently exercise invalid Accept (406), misleading `text/plain;charset=application/json` (415), and an initialize-plus-tools/list batch (400), including combined invalid-header cases. Observe the existing protocol rejection, no published session ID, no retained active/provisional owner or orphan metadata, exited owned children and released generated configuration/profile ownership; exclude a later valid initialize returning 503 because of a rejected predecessor, including after the short test TTL. Observe actual acquisition/disposal and capacity, not merely an absent record or log. Exercise simultaneous initializes at capacity, valid JSON media-type parameters, malformed/oversized JSON and client abort; exclude over-admission, permanent pending reservations or cross-session cleanup. Successful ordinary and managed-CDP initialization retain their existing supported responses.

### AR-004: Validate HTTP authority independently of optional authentication (SEC-002)

**Behavior.** Preserve tokenless local clients and optional bridge bearer authentication, including trusted reverse proxies that authenticate outside the bridge. Do not make a bridge token mandatory merely because the bind address is non-loopback. Independently require an allowed Host and, when Origin is present, an allowed Origin before creating a session or upstream/browser resource. Origin-less native MCP clients are permitted only with an allowed Host. A valid token never bypasses authority validation. This is outer HTTP admission, not a replacement for upstream browser-navigation origin policy or CDP's separate authority/capability rules.

**Acceptance.** Observe 403 for a syntactically valid but unapproved Host or present Origin, including `attacker.invalid`, opaque `null`, lookalike/suffix domains and an allowed Host paired with a hostile Origin; observe zero runtime/child acquisition. Malformed HTTP rejected by the HTTP parser may produce 400, but cannot reach resource allocation. Observe unchanged 401 behavior for missing/incorrect configured bearer credentials; exclude leaking credentials or admitting hostile authorities with a correct token. Authorized local Origin-less requests and explicitly allowed proxy requests complete initialize and a tool call. Apply the admission safeguards to MCP GET/POST/DELETE and existing health/readiness endpoints without changing their configured-token semantics; exclude using a probe as an authentication bypass. Forwarded authority headers do not implicitly grant trust.

### AR-005: Make allowed HTTP addresses an explicit operator contract

**Behavior.** Provide separate process-level allowed-Host and allowed-Origin settings through the bridge's ordinary CLI/environment configuration surface. Their public names are `--http-allowed-hosts <authorities>` / `CLOAK_PLAYWRIGHT_MCP_HTTP_ALLOWED_HOSTS` and `--http-allowed-origins <origins>` / `CLOAK_PLAYWRIGHT_MCP_HTTP_ALLOWED_ORIGINS`. Each accepts a comma-separated list with surrounding entry whitespace removed. CLI overrides environment, which overrides safe defaults; an explicit list replaces that setting's default list rather than silently broadening it. Settings are fixed for the server process and cannot be supplied through per-session initialize metadata.

Host entries are exact Host authority values, including an explicit port where required; Origin entries are exact HTTP(S) origins with scheme and authority, without credentials, path, query or fragment. Matching must not use suffix/substrings or infer permission from DNS resolution. Default Host values cover `localhost`, IPv4 loopback and IPv6 loopback for the actual listening port; default Origins cover those authorities with the configured listener scheme. A port-zero listener uses its assigned port, not zero. A wildcard bind address is not an allowed public authority. Operators explicitly list public/proxy authorities and origins, including every local probe authority they retain when replacing defaults. No permissive `*`, wildcard-domain or validation-disable setting is introduced.

**Acceptance.** Observe that a default local client works unchanged, an explicitly configured `mcp.example.com` authority/origin works, and an unlisted external authority does not. Table-driven cases distinguish default ports, explicit ports and IPv6 bracket syntax without fuzzy matching. Blank lists, empty entries, wildcard entries, malformed authorities and non-origin URLs fail configuration with an actionable non-secret message before resource startup; exclude an empty list disabling validation. CLI/environment conflict cases demonstrate the stated precedence; restarts apply changed settings, while existing requests/sessions do not rewrite policy. Help and generated CLI documentation expose the exact new settings and examples without adding `CLOAKBROWSER_MCP_*` aliases or changing `PLAYWRIGHT_MCP_*` ownership.

### AR-006: Keep proxy credentials out of launch-failure diagnostics (SEC-003)

**Behavior.** A browser launch failure must not disclose configured proxy authentication material through MCP error content, bridge/upstream diagnostic streams, local introspection or a structured error cause visible to a client. Preserve an actionable non-secret failure category and useful non-secret context. Cover supported authenticated SOCKS5 and native HTTP proxy paths, including their encoded credential representations. Do not solve disclosure by weakening proxy authentication, disabling errors, hiding all upstream results or changing upstream tool schemas.

**Acceptance.** Use unique synthetic credential markers, an isolated loopback proxy configuration and a temporary executable that exits immediately. Observe a real installed-upstream launch error in ordinary and relevant managed launch paths; assert absence of raw and supported encoded secret markers in every captured diagnostic surface while a useful failure remains. Exclude a fabricated already-sanitized error as proof or printing real secrets in failure evidence. Exercise credential-free proxies, supported HTTP fallback representation and ordinary successful tool content; exclude corrupting unrelated values. The historical SOCKS5 proof is verified evidence; native HTTP and additional paths require their own new evidence before being marked covered.

### AR-007: Treat stdio EOF as an owner termination path (CODE-001)

**Behavior.** Downstream stdin EOF terminates the running stdio bridge's ownership without requiring a later signal or parent SDK kill escalation. EOF, transport termination and supported signals share the same observable idempotent cleanup guarantees. Successful EOF cleanup exits normally; fatal startup or incomplete cleanup is reported on stderr and cannot be represented as successful termination. No interactive prompt or operational stdout message is introduced.

**Acceptance.** Initialize the packaged CLI against a controlled upstream, end stdin without sending a signal and observe both bridge/upstream exit, removed generated configuration and reusable profile; exclude a test helper's SIGTERM/SIGKILL supplying the cleanup being claimed. Repeat before initialization completes, during a pending call and together with a signal/explicit close; observe one completed cleanup outcome without hanging, double-disposal errors or unrelated process termination. Capture stdout as valid protocol-only output and stderr as diagnostics. A test timeout is a failure, not proof that EOF is supported.

### AR-008: Shutdown must include in-progress HTTP initialization (CODE-002)

**Behavior.** Server-initiated shutdown closes admission before taking its final ownership boundary and accounts for provisional as well as active sessions. Initialization that was already in progress may be drained or cancelled, but cannot create an owner that survives successful shutdown. A later initialize is not admitted after shutdown begins. Repeated/concurrent shutdown requests converge on the same terminal ownership result.

**Acceptance.** Gate ordinary and managed initialization before owner registration, begin shutdown, then release the gate. After shutdown reports success, observe zero active/provisional owners, exited owned children, released generated resources and unusable former owned CDP capabilities/ports; exclude a second close being required to dispose a late owner. Do not assert an incorrect response chronology: the audited order was shutdown started → initialize response completed → shutdown resolved. An already in-flight response may finish while shutdown is draining; successful shutdown with a live owner is never acceptable. Combine this race with disconnect, startup error and existing active sessions; exclude an indefinitely pending initialization, new admission or cross-session resource loss.

### AR-009: Roll back every failed startup handoff (CODE-003)

**Behavior.** Any failure after resources are acquired but before startup is successfully established releases resources acquired for that attempt. Cover preparation, headed/display setup, upstream initialization and outer-transport connection, for ordinary and managed startup. Ownership supplied by another live caller/session must not be mistaken for newly acquired disposable resources. Preserve the original non-secret startup error and report additional cleanup failure rather than mask it. A busy configured profile in ordinary mode is no longer a startup failure: AR-019–020 move that conflict to the browser-requiring tool call without terminating the MCP server. Eager managed CDP still requires exclusive ownership during initialization and applies these startup-rollback guarantees when it cannot obtain it.

**Acceptance.** Inject each fallible boundary independently and observe no retained generated configuration, child or owned lock and successful subsequent use of the same profile; exclude acquiring the same profile failing solely because the rejected attempt retained ownership. Observe actual child termination, not only a removed in-memory reference. Repeat failure and cleanup calls, including caller-owned-resource controls; exclude double-release, deletion of persistent profile contents or disruption of an unrelated owner. Startup errors retain nonzero CLI status without contaminating stdio stdout.

Cover Stable, explicit binary/version pins, unavailable-platform fallback with warning, cache reuse, invalid channel and license/verification failure. Do not automatically retry a cancelled side-effecting call or claim cancellation reverses committed work. Cancellation is request-scoped and must not close other sessions or abort unrelated calls.

**Acceptance.** Use an actual SDK cancellation flow and a controlled upstream that records receipt and gates one side effect. Observe downstream cancellation, upstream abort receipt and prevented uncommitted work where supported; exclude merely rejecting the downstream promise while the upstream silently completes. Cover pre-dispatch cancellation, pending work, managed recovery, duplicate cancellation, late cancellation after a committed effect and subsequent successful calls. Observe that unrelated calls/sessions complete and tool schema/result compatibility remains intact. Do not require rollback of the committed-effect control.

### AR-019: Keep ordinary MCP discovery available when a profile is busy (#179)

**Behavior.** In ordinary stdio and Streamable HTTP mode, a configured persistent profile already owned by another browser/session does not by itself prevent server startup, valid MCP initialization, actual upstream tool discovery or either existing local inspection tool. Do not acquire exclusive browser-profile ownership solely for discovery/inspection; acquire it when an operation actually needs to open/use that browser profile. This correction is the ordinary-mode default, not a new opt-in flag. Preserve other genuine configuration, authentication, capacity and startup errors.

Tool discovery forwards the installed provider's applicable tool names, schemas, pagination and dynamic updates; do not hardcode 72 tools, fabricate a static replacement catalog or publish page-dependent tools that are not actually available. If browser use encounters a live owner, the calling operation returns a normal MCP tool result with `isError: true`, an actionable conflict description, the configured profile directory and available valid owner PID/creation timestamp. Missing/unreadable metadata is identified as unavailable rather than invented or dumped raw. This tool-level conflict does not terminate the MCP server, close its HTTP session, suppress later discovery or disclose credentials. Operations that do not require the profile remain available.

The agreed exception is eager managed CDP: because its initialization already needs a browser to establish verified readiness, it acquires exclusive ownership then. A busy profile still causes the existing non-success managed startup/initialization outcome with complete provisional cleanup under AR-003/008/009; it never publishes a falsely ready browser/capability. This change does not make managed CDP lazy.

**Acceptance.** With valid configuration/authentication and HTTP capacity for both sessions, hold a profile in one owner and start a second ordinary stdio process and two same-process ordinary HTTP sessions against that configured profile. Observe successful initialize, provider-matched paginated tools/list and both existing local inspections before browser use; assert no browser launch/profile-claim acquisition caused solely by those discovery operations. Exclude the former fatal startup/no-browser-tools behavior. Exercise environment-selected profiles and authenticated per-session profile selection. The first operation actually requiring the occupied profile returns `isError: true` with available owner details, not a transport/JSON-RPC exception or process exit; afterward tools/list/inspection and unrelated sessions still work. No third local tool or optional diagnostic schema is introduced. Separately observe eager managed CDP failing cleanly on contention and becoming ready only after successful exclusive ownership; exclude interpreting ordinary discovery availability as a promise of eager CDP readiness. Document the mode distinction and safe retry guidance without copying the issue reporter's version/tool-count assumptions.

### AR-020: Preserve exclusive profile ownership and safe recovery (#179)

**Behavior.** Delaying acquisition does not introduce concurrent browser sharing. At most one logical browser owner may use a configured profile, including simultaneous first-use attempts across supported local processes and HTTP sessions. Acquisition, ownership lifetime and release must remain race-safe. A losing contender, discovery-only client, cancelled acquisition or failed launch may release only resources it actually acquired; it must not delete another live/replacement owner's claim or close that owner's browser. Retain a successful claim while its browser can still use the profile; terminal cleanup releases it only when safe under AR-015.

Preserve existing supported conservative Chromium stale-lock recovery. For configured-profile ownership recovery, reclaim only when the recorded owner is provably dead in the relevant process-identity/liveness context and the claim being reclaimed has not been replaced. Live, malformed, unreadable, permission-indeterminate or otherwise unverifiable owners remain protected with an actionable conflict/unknown-owner outcome.
